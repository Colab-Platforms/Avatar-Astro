● Good question — the polling approach the current code uses is both expensive
  and sluggish. Let me break down what's actually happening and the better
  options.

  What the current code does

  services/youtubeLiveService.ts calls search.list?eventType=live to ask YouTube
  "is this channel live right now?" That's the only way to ask that question
  directly via the Data API — but it costs 100 quota units per call, out of a
  default daily quota of 10,000 units.

  Your refresh loop (darshanRefreshService.ts) runs every 15 minutes = 96
  times/day. For just one temple, that's 96 × 100 = 9,600 units/day — almost
  your entire daily quota consumed checking one channel. With multiple temples,
  you blow through the quota before the day is half over. That's literally why
  the code has the "skip refresh if already checked recently" guard and warns
  about dev-server restarts burning quota — it's working around a fundamentally
  expensive polling design, not a bug.

  It's also slow: a stream going live is only detected up to 15 minutes late,
  because you're polling on a timer instead of being told immediately.

  Better approach: push notifications instead of polling

  YouTube channels support WebSub (PubSubHubbub) — you subscribe once to a
  channel's feed via Google's hub, and whenever that channel publishes or
  updates a video (including a livestream going live), Google POSTs a 
  notification to a callback URL you host. No quota cost for the notification
  itself, and it arrives in seconds, not up to 15 minutes late.

  Flow:
  1. Subscribe each temple's channel: POST 
  https://pubsubhubbub.appspot.com/subscribe with your callback URL and the
  channel's feed topic. Subscriptions lease for a few days, so you re-subscribe
  periodically (a cheap cron, no API quota involved).
  2. When a video is published/updated, Google POSTs an Atom XML payload
  containing the videoId to your callback endpoint.
  3. You confirm it's actually live + embeddable with
  videos.list?part=liveStreamingDetails,status&id=<videoId> — only 1 quota unit,
  and only when something actually happened.
  4. Detecting when the stream ends still needs a cheap check — but only on the
  one videoId you know is live, not a channel-wide search. You can either poll
  that single video every minute or two (1 unit each — trivial) or rely on the
  fact that YouTube also fires a WebSub update when the broadcast's status
  changes.

  Net effect: quota cost drops from ~100/check to ~1/check, and status updates
  go from "up to 15 min late" to "near real-time."

  Trade-off: this needs a public HTTPS endpoint Google can reach (fine in
  production; for local dev you'd need something like ngrok, or just skip WebSub
  in dev and fall back to polling).

  Simpler fallback if you don't want a public webhook yet

  If adding a public callback endpoint is more infra than you want right now,
  there's a cheaper polling substitute: use playlistItems.list on the channel's
  uploads playlist (~1-5 units) to get the most recent video, then check that
  single video's liveBroadcastContent field via videos.list (1 unit). That
  assumes the live stream is always the channel's most recent upload — true for
  most temple darshan channels. This isn't push-based, but it cuts the cost by
  ~95%, so you could poll every 1-2 minutes instead of 15, for the same quota
  budget, no webhook required.

  My recommendation: start with the cheap-polling fix (quick, no new infra) now,
  and move to WebSub later if you want true real-time updates and are OK
  hosting a public webhook.

  fields into the Prisma Temple model)?

● Let me walk through exactly what "subscribing" means here mechanically, since
  it's a different model than a normal API call.

  The model: hub, topic, subscriber

  WebSub (formerly PubSubHubbub) has three parties:
  - Topic — the thing you want updates about. For a YouTube channel, that's a
  URL like https://www.youtube.com/xml/feeds/videos.xml?channel_id=UCxxxxxxxx
  (an Atom feed of that channel's videos).
  - Hub — a middleman server that YouTube uses to broadcast updates. For YouTube
  it's always https://pubsubhubbub.appspot.com/subscribe.
  - Subscriber — you (your backend), which wants to be notified when the topic
  changes.

  Instead of you repeatedly asking YouTube "anything new?", you tell the hub
  once: "when this topic changes, POST the update to this URL of mine." The hub
  then does the polling/watching on YouTube's internal side (their problem, not
  your quota), and pushes to you.

  Step by step

  1. You expose a callback endpoint on your backend, e.g. POST 
  https://yourdomain.com/api/darshan/youtube-webhook. This must be publicly
  reachable over HTTPS (Google's servers need to hit it from the internet — this
  is why local dev needs ngrok or similar).

  2. You send a subscription request to the hub:
  POST https://pubsubhubbub.appspot.com/subscribe
  Content-Type: application/x-www-form-urlencoded

  hub.callback=https://yourdomain.com/api/darshan/youtube-webhook
  hub.topic=https://www.youtube.com/xml/feeds/videos.xml?channel_id=UCxxxxxxxx
  hub.verify=sync
  hub.mode=subscribe
  hub.lease_seconds=432000
  (one request per temple's channel)

  3. The hub verifies you actually own that callback URL (so random people can't
  subscribe your server to spam). It does this by sending your own endpoint a
  GET request like:
  GET https://yourdomain.com/api/darshan/youtube-webhook?hub.mode=subscribe&hub.
  topic=...&hub.challenge=abc123&hub.lease_seconds=432000
  Your endpoint must respond with HTTP 200 and the exact hub.challenge value 
  echoed back in the response body. That's the whole handshake — it just proves
  you control that URL. Once that round-trip succeeds, the subscription is
  active.

  4. From then on, whenever that channel's feed changes (new video published, or
  an existing video's metadata changes — which includes a stream transitioning
  to "live"), the hub POSTs an Atom XML payload to your callback URL,
  unprompted:
  <feed xmlns="http://www.w3.org/2005/Atom" 
  xmlns:yt="http://www.youtube.com/xml/schemas/2015">
    <entry>
      <yt:videoId>dQw4w9WgXcQ</yt:videoId>
      <yt:channelId>UCxxxxxxxx</yt:channelId>
      <title>Live Darshan</title>
      <published>...</published>
      <updated>...</updated>
    </entry>
  </feed>
  Your webhook handler parses out videoId, then does the cheap confirm call
  (videos.list?part=liveStreamingDetails,status&id=<videoId>, 1 quota unit) to
  check it's actually liveBroadcastContent: "live" and embeddable, and writes
  isLive=true, currentLiveVideoId to your DB right then. No polling loop
  involved — this handler just sits there and reacts when invoked.

  5. The subscription expires after hub.lease_seconds (you can request up to a
  few days). Before it expires, you re-send the same subscribe request to renew
  — a trivial cron job, no YouTube Data API quota cost since it talks to the
  hub, not the Data API.

  6. Detecting "stream ended": WebSub doesn't give you a distinct "went offline"
  event — but when a live broadcast ends, YouTube typically updates that
  video's entry again (title/metadata change), which re-fires a notification to
  you. As a safety net, you can still do a cheap videos.list check (1 unit) on
  the currently-known-live videoId every minute or two, instead of channel-wide
  search.list (100 units) — way cheaper even as a fallback.

  Why this is better than what you have

  Right now your server initiates every check ("poll"). With WebSub, Google's
  hub initiates the check, and only tells you something when there's actually
  something to tell — you stop paying the 100-unit search.list tax entirely, and
  you find out within seconds instead of up to 15 minutes late.

  The catch for your setup

  This only works if your backend has a stable public HTTPS URL reachable from
  Google's servers. If you're deployed (not just local dev), this is
  straightforward. If you're still mostly developing locally, you'd need a
  tunnel (ngrok, Cloudflare Tunnel) during dev, or just keep the cheap-polling
  fallback for local and switch to WebSub in production.

  Want me to implement the cheap-polling fallback first (no infra changes
  needed) and leave WebSub as a documented follow-up for when you're deployed?
