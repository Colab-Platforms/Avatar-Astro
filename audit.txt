  ### Defects in the lifecycle
  - **B1 (BROKEN, race): accept, reject and end can overwrite each other.**
    - `requireRequestedSessionForAstrologer` (L187-199) reads with the global
  `prisma`, not `tx`, and sits outside any lock.
    - The later `tx.chatSession.update` at L222-225 has `where: { id }` only,
  with no `status: "REQUESTED"` guard. The same applies to `rejectSession` at
  L236-239.
    - A sweep TIMEOUT or a user cancel landing between the check and the update
  can be silently overwritten. An ENDED session can be turned back into ACTIVE,
  which fails only if the unique index happens to be violated. A reject racing
  an accept can mark an ACTIVE session ENDED while the reservation stays HELD, a
  leak. Because `registerSession` is also called, billing would then run on a
  dead state.
    - Fix: use `updateMany({ where: { id, status: "REQUESTED" } })` and check
  `count`.
  - **B2 (BROKEN, race): `billing.endSession` (L242-264) is not atomic.** It
  does a `findUnique`, then `releaseReservation`, then an unguarded `update`.
  Two concurrent ends, or a tick racing an end, can both pass the ENDED check,
  so `chat:ended` can be emitted twice and the final update can overwrite
  `endedReason`. `tick` also reads the session before settling, so a tick that
  started just before an end can still settle a charge after the reservation is
  released (`reservation` is re-fetched with status HELD, which narrows this but
  does not close it).
  - **B3 (PART): the "busy" error is misleading.** If the user is busy, or the
  astrologer already has any REQUESTED, ACTIVE or PAUSED session from anyone,
  the second `startSession` fails with the generic "You already have a pending
  or active chat." (L181). There is no distinct "astrologer busy" error or
  presence value. `isOnline` is a manual toggle
  (`chat.astrologer.route.ts:70-82`) plus socket-connection presence; there is
  no "busy" status.
  - **B4 (MISS): no guard against a user starting a chat with their own
  astrologer profile.** `startSession` never compares `profile.userId` with
  `userId`.
  - **B5 (PART): the startSession wallet check is advisory.** `startSession`
  checks the balance but `acceptSession` re-checks it inside the transaction
  (L212-216). That is fine, but the wallet read at L212 is not locked against
  concurrent reservations unless `createReservation` handles it; I did not
  verify that in `wallet.service.ts`.

  ## 4. Other findings
  - **Free-seconds claim.** In `tick`, `claimFreeSeconds` (`billing.ts:179`)
  happens before `settleFromReservation`. If settle throws, the free seconds are
  already consumed and the next tick recomputes from the unchanged
  `lastBilledAt`, so free seconds could be double-claimed. I did not read
  `claimFreeSeconds` to see whether it is idempotent, so UNK.
  - **Silent ack errors.** Socket errors are returned as `err.message` strings
  in the ack, which can expose internal text such as Prisma errors, because the
  catch passes any `Error` message.
  - **Heartbeat load.** Every `chat:heartbeat` and `chat:typing` runs a
  `resolveActor` DB query with two includes, per event per 10s per participant.
  - **Resume cost.** `recordHeartbeat` triggers `maybeResumeFromPause` (a DB
  read) on every heartbeat, even for ACTIVE sessions.
